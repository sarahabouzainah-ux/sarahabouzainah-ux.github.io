01 — The Problem

No system. No source of truth. Just a PDF.

When I joined Valeo in 2021, there was no design system, no shared component library, and no defined visual language for digital products. Designers worked independently across projects, each making their own decisions about spacing, color, and component structure. The only starting point was a brand guidelines PDF.

My first project had to be built without a system. I defined a color combination I believed was right for the product, applied it to real screens, and tested it in context — checking visibility, contrast, and clarity under actual working conditions. Those colors survived the test and became the formal primary and secondary palette, already aligned with what the brand guidelines had defined.

"Instead of defining a system in isolation, I validated it through real product work first. The first project became the first test case for the design system before the design system existed."

02 — Understanding the Users & Context

Before deciding how components look, understand who uses them.

The tools we were designing for are used by engineers and project managers dealing with complex, data-dense workflows. Through observation and early project experience, I collected findings that shaped every visual and structural decision in the system.

🗜️
Space is critical
Users needed to see a lot of information on one screen without scrolling. Every padding value, every component height had to earn its space — compact but not cramped.
👁️
Color blindness is real
We discovered a significant proportion of users had color vision deficiencies. WCAG compliance became non-negotiable and shaped how we communicated state — never through color alone.
📊
Data density, not decoration
The tools carry tables, forms, dashboards, and risk matrices. The style needed to be formal and functional — precise, clear typographic hierarchy, no visual noise competing with data.
03 — Building the Foundation

Get the foundation wrong and everything built on it will be wrong.

The most critical stage wasn't building components — it was defining the primitives everything else would inherit from. A mistake here would cascade across every component in every product.

1
Framework alignment — PrimeNG
An early agreement with the frontend team to use PrimeNG gave the system its first structural anchor. It defined which icon set to adopt and gave me a clear map of which components needed designing. This kept design and development tightly aligned from day one.
2
Color system — shades, states, and accessibility
Starting from the validated primary and secondary colors, I built complete shade scales following the color-50 through color-900 convention. These were defined as design tokens in Figma and simultaneously fed into the SCSS files on the dev side — both progressing in parallel. State colors (error, success, info, warning) were defined alongside and tested across color blindness simulation tools for all major deficiency types.
3
Spacing, typography, and border radius
Spacing was not defined in isolation. The input, dropdown, and button components all needed to align on the same row height — so I designed those components first, defined the element dimensions for readability, then derived the spacing values that made them coherent. Style choices landed on compact, formal, and precise.
4
Parallel SCSS authoring
I wrote the cascade styles in parallel with the Figma design system. When making design decisions, I was simultaneously thinking about how they'd be expressed in code. Class names in Figma matched the SCSS — a token update could flow directly to the running product by editing one file.
🎨Foundation — Color scales, spacing tokens, typography system

Color shade scales (50–900), state colors, spacing scale, and typography hierarchy — the primitives everything else inherits from.

04 — Building the Component Library

Components built with constraints in mind, not after the fact.

With the foundation locked, component work started with the most frequently used elements — form inputs, buttons, dropdowns, and data tables. PrimeNG gave a baseline; the job was styling them to the system's tokens and documenting every state, variant, and usage rule in Figma.

🧩Core components — Inputs, buttons, dropdowns
📋Data components — Tables, filters, pagination

Core interaction and data-heavy components were prioritised first as they appear in every tool.

The handoff worked through matched class naming between Figma and SCSS. When a component style updated, the corresponding SCSS class carried that change to the running product. The main friction: live products couldn't always absorb updates immediately. This mismatch was flagged to the business as a known risk and managed through release planning.

Planned in milestones. Adopted across teams.

With 8 products already in progress when the system launched, I planned the rollout in three milestone releases — each timed to add value without disrupting live delivery.

Adoption was driven by team alignment, not mandate. All 5 designers agreed on the system as the shared source of truth and each aligned with their dev teams. When Valeo's brand changed in Release 3, the token architecture absorbed it cleanly — most changes were token value updates, not component rebuilds.

06 — Key Decisions

The choices that shaped the system.

Framework
Anchor to PrimeNG early
Aligning with the frontend team's chosen framework before building anything gave the system a clear component scope and a shared vocabulary from day one. It prevented designing components that couldn't be implemented as intended.
Process
Validate through real projects, not a workshop
The color system was tested on a live project before being formalised. This grounded every early decision in actual user-facing context rather than abstract design principles.
Accessibility
WCAG from the start, not as a retrofit
Knowing that our user base included color-blind users, accessibility was built into the foundation — contrast ratios, color blindness simulation, and non-color-dependent state communication — before any components were designed.
Engineering
Write the SCSS alongside the Figma
Authoring cascade styles in parallel with the design system kept both in sync and gave design decisions a code-reality check. Class name alignment between Figma and SCSS meant updates propagated cleanly to running products.

08 — What I'd Do Differently

Reflections from building it.

01

Invest more in semantic variables from the start

I'd spend more time investigating semantic variable architecture before building the first components. Some early color and spacing decisions had to be revisited when later components revealed dependencies we hadn't anticipated. The token structure made updates manageable, but deeper semantic planning upfront would have reduced the rework.

02

Tokens make change survivable

The decision to build on design tokens paid off most clearly when Valeo's brand identity changed. What could have been a full system rebuild became largely a token value update — design and code updated together. This is the real value of a token-first system: resilience to change.

03

Real constraints make better systems than ideal ones

The space constraints, the color blindness discovery, the PrimeNG framework — none of these were ideal conditions. But designing within them produced a system that actually fit the users and teams using it.
